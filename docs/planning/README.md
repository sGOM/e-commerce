# 신규 기능 기획 — 마켓컬리 벤치마킹

> 작성일: 2026-07-04
> 작성자: 프로덕트 기획(planner)
> 상태: Draft — 우선순위/범위는 오너 검토 후 확정

## 배경

현재 이커머스 플랫폼은 마켓플레이스 MVP(멀티 셀러 주문, 쿠폰/포인트, 게스트 주문, 셀러 정산)까지
완료된 상태다(`PRD.md`, `README.md`, `docs/SERVER_ARCHITECTURE.md` 참고). 여기서부터는 "산다"를
넘어 "탐색·재방문·신뢰"를 강화하는 커머스 경험이 필요하다. 마켓컬리는 신선식품 새벽배송에서
출발했지만, 우리가 참고할 차별점은 배송 자체보다 **탐색·신뢰·재구매를 만드는 장치**들이다:

- 포토리뷰 중심의 구매 후기(신뢰)
- 재입고 알림(수요 놓치지 않기)
- 기획전/컬렉션 큐레이션(발견)
- 타임딜(긴급성)
- 배송 슬롯 예약(예측 가능한 배송)
- 유료 멤버십(록인)
- 선물하기(신규 유입 채널)
- 정기배송(반복 구매 자동화)

이 문서는 위 8개 기능 후보를 **우리 아키텍처(SubOrder 분리, 게스트/회원 구분, 원자적 재고 UPDATE,
정책 DB 행, 서버 금액 계산)에 맞춰** 정의한다. 이미 구현된 기능(상품검색, 인기상품, 쿠폰/포인트,
정산 등)은 재정의하지 않고 전제로 삼는다.

> **진행 현황(2026-07-05 갱신)**: 아래 8개 후보는 모두 코드베이스에 구현되어 있다(`review`,
> `restock`, `promotion`(컬렉션), `flashsale`, `delivery`(권역/슬롯), `membership`(유료 구독),
> `subscription`(정기배송), 선물하기 프론트 `GiftClaimPage` 등). 후속 브레인스토밍은
> [wishlist-price-alert.md](./wishlist-price-alert.md) §0 을 참고.
>
> 아직 코드에 없는 결제·계정·운영 과제 백로그는 [../ROADMAP.md](../ROADMAP.md) 에서 관리한다.

## 다른 서브에이전트를 위한 안내

- 이 디렉터리는 **"무엇을·왜"** 를 정의한 기획 문서다. **"어떻게 구현할지"는 각 전문 에이전트가
  결정**한다.
  - 데이터 모델·API 상세 설계·트랜잭션/동시성 전략: **spring-expert** — 각 문서의 "데이터 모델/API
    개략"은 출발점일 뿐, 실제 컬럼 타입·인덱스·마이그레이션 버전은 spring-expert가 확정한다.
  - 화면 톤/컴포넌트/접근성: **uiux-expert** — `docs/design/storefront-ui-spec.md`의 토큰·컴포넌트
    체계를 따른다.
  - 프론트 구현: **react-expert** — 각 문서의 "프론트 화면/플로우 개략"을 참고해 라우트·상태관리를
    설계한다.
- 문서마다 "오픈 이슈"는 기획 단계에서 결정이 필요한 지점이다. 구현 전 프로덕트 오너와 확정 필요.
- 기존 도메인과 충돌 가능성이 있는 지점(예: 배송비 모델 부재, 정기결제 인프라 부재)은 트레이드오프와
  함께 명시했다.

구현 난이도) 기반 P0/P1/P2. RICE의 Reach/Confidence는 서비스 초기 단계라 정성적으로만 반영.

|---|---|---|---|---|---|---|

| **P1** | 기획전/컬렉션 큐레이션 | 높음 | 낮음 | MD 편집 진열로 발견성↑. 신규 도메인이지만 기존 Product 참조뿐이라 단순 | [curated-collections.md](./curated-collections.md) | ✅ 구현됨 |

### 단계적 롤아웃 제안 (2026-07-04 원안)
1. **1차(P0)**: 리뷰/포토리뷰, 재입고 알림 — 기존 도메인에 최소 침습, 신뢰/재방문 개선.
2. **2차(P1)**: 컬렉션 큐레이션 → 타임딜 → 배송 슬롯 순. 컬렉션은 순수 신규 도메인이라 리스크가
   낮아 먼저, 타임딜은 재고 동시성 패턴을 재사용하되 정산 정책 결정 후, 배송 슬롯은 물류 전제 확정 후.
3. **3차(P2)**: 정기결제 인프라(빌링키 발급/저장, 실패 재시도, 웹훅)를 **공통 기반**으로 먼저 구축한
   뒤 멤버십과 정기배송을 순차 개발. 선물하기는 별도 트랙으로 언제든 착수 가능.

> **진행 현황(2026-07-05)**: 위 8개 + 위시리스트/가격인하 알림, 누적구매 로열티 등급, 장바구니 이탈
> 리마인드까지 모두 구현 완료됐다. 리텐션 3종의 확정 정책은 각 기획서와 `PRD.md` §11에 있다. 남은
> §0 후보(리퍼럴, 리뷰 이벤트)는 자동 인센티브 지급을 수반하므로, 아래 "공통 오픈 이슈 5"의 어뷰징
> 방지 원칙이 먼저 확정된 뒤 개별 기획 문서로 발전시키는 것을 제안한다.

## 공통 오픈 이슈 (여러 기능에 걸침)

1. **정기결제(빌링) 인프라 부재**: 멤버십·정기배송 모두 카드 빌링키 발급/저장/재시도가 필요하다.
   토스페이먼츠 빌링 API 연동 여부와 시점을 먼저 결정해야 한다.
2. **배송비 모델 부재**: 현재 PRD/구현에 배송비(shipping fee) 개념이 없어 보인다(무료배송으로
   추정). 멤버십의 "무료배송 혜택", 배송 슬롯의 "새벽배송 추가요금" 등을 기획하려면 배송비 모델
   확정이 선행되어야 한다.
3. **알림 채널 인프라 부재**: 재입고 알림·선물하기 공유·정기배송 실패 안내 모두 이메일/푸시 발송이
   필요하다. 현재는 이메일 발송 인프라가 없어 보이므로, 최소 "인앱 알림함"으로 시작하고 이메일은
   후속 과제로 분리하는 것을 제안한다. (위시리스트 가격 인하 알림도 동일 원칙을 따른다.)
4. **셀러 참여 범위**: 컬렉션/타임딜을 관리자만 편성할지, 셀러도 신청할 수 있게 할지는 운영 정책
   결정이 필요하다(각 문서에 개별 오픈 이슈로 기록).
5. **인센티브 자동 지급 어뷰징 방지 원칙 — ✅ 확정(2026-09-25, "표준 방어")**: 리퍼럴 보상·리뷰 이벤트 등
   행동 기반 자동 쿠폰/포인트 지급 기능은 모두 아래를 공통으로 지킨다.
   - **1인 1회**: 회원 + 연락처 기준으로 같은 보상의 중복 지급을 막는다.
   - **자기추천 차단**: 추천인·피추천인의 연락처 또는 배송지가 같으면 보상하지 않는다.
   - **구매확정 후 지급, 취소·환불 시 회수**: 가입·주문 생성만으로는 지급하지 않고 구매확정(DELIVERED) 시점에 지급,
     이후 취소·환불되면 지급분을 회수한다(포인트는 lot 회수, 쿠폰은 미사용분 회수).
   - **1인 월 지급 상한**: 기능별 상한을 정책 행(DB)으로 두고 관리자가 조정한다.
