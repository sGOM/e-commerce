# 정기배송 구독

> 우선순위: **P2** (Could — 정기결제 인프라 공유, 배치 복잡도 높음)
> 관련 도메인: `order`(자동 주문 생성), `payment`(정기결제, `subscription-membership.md`와 공유),
> `catalog`(재고 확인)

## 1. 개요 및 배경

마켓컬리는 생수·우유·반찬 등 소모품을 주기적으로 자동 주문해주는 정기배송을 운영한다. 이는
재구매를 자동화해 이탈 없이 반복 매출을 만드는 장치다. 우리 플랫폼은 현재 매 주문을 고객이
직접 생성해야 하며, 자동 반복 주문/결제 개념이 없다. `subscription-membership.md`와 마찬가지로
**정기결제(빌링) 인프라**가 필요하므로, 두 기능은 인프라를 공유하되 별도 기능으로 정의한다.

## 2. 목표 및 성공지표

- 목표: 고객이 특정 상품 옵션을 주기(예: 2주)로 자동 재주문하도록 설정하고, 시스템이 주기마다
  자동으로 주문을 생성·결제한다.
- 성공지표(제안)
  - 정기배송 등록 건수, 3회 이상 유지율(구독 리텐션)
  - 자동 주문 성공률(재고/결제 실패로 인한 스킵 비율)
  - 정기배송 고객의 LTV vs 일반 고객 비교

## 3. 유저 스토리 & 수용기준(AC)

### US-1. 회원은 상품을 정기배송으로 등록한다
- AC1: 상품 옵션, 수량, 주기(일 단위, 예: 7/14/30일), 배송지, 결제수단(빌링키)을 설정한다.
- AC2: 등록 즉시 첫 회차는 일반 주문처럼 즉시 결제·주문 생성할지, 다음 주기부터 시작할지 선택
  가능(기본값은 즉시 시작 제안).

### US-2. 회원은 정기배송을 일시정지/재개/해지할 수 있다
- AC3: 일시정지 중에는 자동 주문이 생성되지 않고, 재개 시 다음 청구일부터 재개된다.
- AC4: 해지 시 예정된 다음 회차부터 생성되지 않는다(이미 생성된 주문은 영향 없음).
- AC5: 다음 배송일 도래 T일 전(정책값)까지는 건너뛰기(스킵 1회)를 요청할 수 있다.

### US-3. 배치가 주기 도래 건을 자동 처리한다
- AC6: `nextOrderAt` 도달 건에 대해 재고를 확인하고, 가용하면 주문 생성 → 정기결제 시도 →
  성공 시 일반 주문과 동일한 `Order/SubOrder` 라이프사이클을 따른다.
- AC7: 재고 부족 시 해당 회차는 스킵하고 회원에게 알림(인앱), `nextOrderAt`은 다음 주기로 갱신.
- AC8: 결제 실패 시 N회 재시도 후 실패하면 해당 회차 스킵 + 알림, 연속 실패 M회 누적 시 구독을
  자동 `PAUSED`로 전환(카드 만료 등 방치 방지).
- AC9: 가격은 **주문 생성 시점(회차마다) 현재가**를 기준으로 한다(구독 등록 시점 가격 고정 아님 —
  기존 "장바구니 가격은 조회 시점 현재가" 원칙과 일관).

### US-4. 회원은 정기배송 이력을 확인한다
- AC10: 마이페이지에서 정기배송 설정 목록과 각 회차별 생성된 주문 링크를 볼 수 있다.

## 4. 정책/규칙 & 예외

- **가격 변동**: 상품가가 오르면 다음 회차부터 반영(스냅샷 고정 아님) — 사전 안내가 필요할 수
  있음(오픈 이슈).
- **품절/판매중지**: 상품이 완전히 판매중지(`HIDDEN`)되면 해당 정기배송은 자동으로 `PAUSED` 전환 +
  회원에게 대체 상품 추천 없이 안내만(추천은 범위 밖).
- **쿠폰/포인트**: 자동 생성 주문에는 쿠폰 자동 적용 없음(사람이 선택하는 액션이라 자동화 대상
  아님). 포인트 자동 사용도 기본 미적용(옵션으로 "포인트 자동사용 설정"을 둘지는 오픈 이슈).
- **주문 취소**: 자동 생성된 개별 회차 주문은 일반 주문과 동일하게 취소 가능(구독 자체가 취소되는
  것은 아님).

## 5. 데이터 모델 / API 개략 (spring-expert 참고)

```
DeliverySubscription
  id, userId(FK), productOptionId(FK), quantity
  cycleDays, nextOrderAt, status(ACTIVE/PAUSED/CANCELED)
  addressId(FK), billingKeyId(FK, membership과 공유 가능한 빌링키 테이블 참조)
  consecutiveFailureCount

DeliverySubscriptionHistory
  id, subscriptionId(FK), attemptedAt, result(ORDER_CREATED/SKIPPED_OUT_OF_STOCK/PAYMENT_FAILED)
  orderId(nullable FK)
```

- **빌링키 재사용**: `subscription-membership.md`의 `MembershipBillingKey`와 별개 도메인이지만
  "카드 등록 → 빌링키 발급"이라는 인프라는 공유하는 것을 제안(중복 카드 등록 UX 방지). 공용
  `UserBillingKey` 테이블로 통합할지, 도메인별로 분리할지는 spring-expert와 조율 필요.
- **배치**: 매일 새벽 실행되는 스케줄러가 `nextOrderAt <= today`인 활성 구독을 조회 →
  `OrderService`의 기존 주문 생성 로직(가능하면 내부 API 재사용, 결제만 자동화 어댑터로 대체)을
  호출. 기존 `SettlementScheduler` 패턴과 동일한 `@ConditionalOnProperty` 토글 방식 제안.
- 신규 마이그레이션: `delivery_subscriptions`, `delivery_subscription_histories`.

### API 개략
| 메서드 | 경로 | 설명 | 인증 |
|---|---|---|---|
| POST | `/api/me/delivery-subscriptions` | 정기배송 등록 | 회원 |
| GET | `/api/me/delivery-subscriptions` | 내 정기배송 목록 | 회원 |
| PATCH | `/api/me/delivery-subscriptions/{id}/pause` · `/resume` | 일시정지/재개 | 회원 |
| DELETE | `/api/me/delivery-subscriptions/{id}` | 해지 | 회원 |
| POST | `/api/me/delivery-subscriptions/{id}/skip-next` | 다음 회차 건너뛰기 | 회원 |
| GET | `/api/admin/delivery-subscriptions?status=` | 관리자 현황 조회 | 관리자 |

## 6. 프론트 화면/플로우 개략 (react-expert · uiux-expert 참고)

- **상품 상세**: "정기배송으로 구매" 옵션(일반 담기 버튼 옆 보조 버튼) → 주기 선택 모달.
- **마이페이지**: "정기배송 관리" 탭 — 상품별 카드(다음 배송일, 주기, 일시정지/해지/스킵 액션),
  회차별 이력(성공/스킵 사유) 타임라인.
- **알림**: 회차 스킵/결제 실패 시 인앱 알림(재입고 알림과 동일 `Notification` 엔티티 재사용 제안).

## 7. 기존 기능과의 연계/영향

- **order 도메인**: 자동 생성 주문도 기존 `Order/SubOrder/OrderItem` 구조를 그대로 따른다(주문
  생성 경로만 "구독 배치"로 추가, 도메인 모델 변경 없음). 다만 "주문 생성 트리거가 사람이 아닌
  배치"라는 점에서 감사로그 기록 주체 표기(시스템 액터)에 대한 처리가 필요.
- **catalog 도메인**: 회차마다 재고 원자적 UPDATE를 그대로 재사용(신규 로직 불필요, 실패 시
  스킵 처리만 추가).
- **payment 도메인**: `subscription-membership.md`의 정기결제 인프라를 공유. 별도로 먼저 구현하지
  않는다(중복 투자 방지를 위해 두 기능의 착수 순서를 함께 계획할 것을 제안).

## 8. 범위 (In / Out of scope)

**In scope**
- 단일 상품 옵션 정기배송 등록/일시정지/해지/스킵, 배치 자동 주문 생성, 실패 처리·알림

**Out of scope**
- 여러 상품을 묶은 정기배송(정기 박스/큐레이션 배송) — 후속 확장 여지로만 남김
- 가격 고정(구독 시점 가격 유지) 옵션
- 자동 포인트/쿠폰 적용

## 9. 오픈 이슈 (결정 필요)

1. **정기결제 인프라 우선순위**: 멤버십과 정기배송 중 어느 것을 먼저 만들지, 빌링키 인프라를
   공용으로 설계할지 개별로 할지.
2. **가격 변동 고지 의무**: 회차마다 현재가로 청구할 경우, 법적/신뢰 관점에서 사전 고지가
   필요한지(정기결제 관련 소비자보호 이슈 검토 필요 — 법무 검토 권장).
3. **연속 실패 임계치**: 자동 일시정지 전 재시도 횟수/기간 정책값.
4. **감사로그 액터 표기**: 배치가 생성한 주문의 "행위자"를 시스템으로 어떻게 표기할지 기존
   `AuditLogFilter` 설계와 조율 필요.
