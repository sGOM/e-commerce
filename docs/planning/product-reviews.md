# 상품 리뷰 / 포토리뷰

> 우선순위: **P0** (Must)
> 관련 도메인: `catalog`(Product), `order`(Order/OrderItem), `point`(리뷰 적립), `admin`

## 1. 개요 및 배경

마켓컬리는 "왜 이 상품을 사야 하는가"에 대한 답을 포토리뷰로 채운다. 별점·후기·사진이 상세페이지
상단 근처에 밀도 높게 노출되고, 구매 인증된 리뷰만 허용해 신뢰도를 높인다. 우리 플랫폼은 현재
상품 상세에 리뷰/평점이 전혀 없어(`PRD.md` 2.2 비목표에 "리뷰·평점 상세" 명시) 구매 결정을 도울
사회적 증거(social proof)가 없는 상태다. 멀티 셀러 마켓플레이스 특성상, 리뷰는 셀러 신뢰도에도
직결되므로 우선순위가 높다.

## 2. 목표 및 성공지표

- 목표: 배송완료 주문에 대해 리뷰 작성을 유도하고, 상품 탐색/상세 단계에서 평점·리뷰를 신뢰
  신호로 노출한다.
- 성공지표(제안, 확정은 오너 결정)
  - 배송완료 주문 대비 리뷰 작성률(리뷰 전환율)
  - 포토리뷰 비율
  - 리뷰 노출 상품의 상세페이지 → 구매 전환율 개선폭

## 3. 유저 스토리 & 수용기준(AC)

### US-1. 구매자는 배송완료된 상품에 대해 리뷰를 남길 수 있다
- AC1: `OrderItem`이 속한 `SubOrder.status = DELIVERED`인 경우에만 리뷰 작성 가능하다.
- AC2: 하나의 `OrderItem`당 리뷰는 최대 1개다(재작성 아닌 수정만 가능).
- AC3: 평점(1~5, 필수) + 텍스트(필수, 최소 10자) + 사진(선택, 최대 5장)을 입력한다.
- AC4: 본인이 구매하지 않은 `OrderItem`, 또는 타인의 주문에 대해서는 403이 아닌 404(존재 은닉,
  기존 `cancelSubOrder` 컨벤션과 동일)로 응답한다.
- AC5: 게스트 주문 건은 리뷰 작성 불가(회원 전용) — 게스트는 로그인/주문 클레임(`/api/orders/claim`)
  후 회원 자격으로 작성 가능.

### US-2. 구매자는 본인 리뷰를 수정/삭제할 수 있다
- AC6: 작성자 본인만 수정/삭제 가능(소유권 검증).
- AC7: 삭제 시 이미 지급된 리뷰 적립 포인트는 회수하지 않는다(운영 정책, 오픈 이슈 참고).

### US-3. 고객은 상품 목록/상세에서 평점과 리뷰를 확인할 수 있다
- AC8: 상품 카드/상세에 평균 평점(소수 1자리)과 리뷰 개수를 노출한다.
- AC9: 상세페이지 리뷰 탭에서 최신순/평점높은순/사진리뷰만 정렬·필터링할 수 있다.
- AC10: 신고 누적 또는 관리자 숨김 처리된 리뷰는 목록/평균 평점 계산에서 제외한다.

### US-4. 고객은 부적절한 리뷰를 신고할 수 있다
- AC11: 로그인 사용자는 리뷰를 신고할 수 있다(사유 선택). 동일 리뷰 중복 신고는 1회로 집계.
- AC12: 신고 누적 임계치(예: 5건, 정책값) 도달 시 자동으로 `REPORTED` 상태가 되어 노출은 유지하되
  관리자 검토 큐에 노출된다(자동 숨김 아님 — 오탐 방지).

### US-5. 관리자는 리뷰를 검수/숨김 처리할 수 있다
- AC13: 관리자는 리뷰 목록을 검색(상품/작성자/신고여부)하고 `HIDDEN` 처리할 수 있다.
- AC14: `HIDDEN` 리뷰는 고객에게 노출되지 않지만 작성자 본인에게는 "숨김 처리됨" 안내와 함께 보인다.

### US-6. 리뷰 작성 시 포인트를 적립받는다
- AC15: 텍스트 리뷰는 정책값 A포인트, 포토 리뷰는 정책값 B포인트(A보다 큼) 적립.
- AC16: 동일 주문/상품에 대한 어뷰징(삭제 후 재작성 반복) 방지를 위해 `OrderItem`당 적립은 최초 1회만.

## 4. 정책/규칙 & 예외

- **작성 가능 조건**: `SubOrder.status = DELIVERED` (배송 완료). 배송 후 자동 구매확정 개념이
  없다면 DELIVERED 시점을 그대로 기준으로 삼는다(오픈 이슈 참고).
- **리뷰 가능 기간**: 배송완료 후 N일(정책값, 기본 예: 90일) 이내로 제한 권장 — 상품 스냅샷과
  시의성 유지. 기간 경과 후에는 작성 폼 비노출.
- **환불/취소된 주문**: SubOrder가 이후 취소/환불되어도 이미 작성된 리뷰는 유지한다(구매 자체는
  사실이었으므로). 단, 작성 시점에 이미 취소 상태라면 애초에 리뷰 작성 자격이 없다.
- **삭제된 상품**: 상품이 `HIDDEN`/삭제되어도 리뷰는 유지하되, 비공개 상품 페이지 접근 시 처리
  방식은 상품 도메인 정책을 따른다.
- **포토 업로드**: 이미지 스토리지(S3 등)는 이 문서 범위 밖. 업로드 API는 별도 파일 업로드
  인터페이스를 전제로 하고, 리뷰 엔티티는 업로드된 URL만 참조한다.
- **예외**: 같은 상품을 여러 옵션으로 여러 번 구매한 경우 `OrderItem` 단위로 리뷰가 각각 남을 수
  있다(같은 상품에 여러 리뷰 허용, 단 동일 OrderItem 재작성만 금지).

## 5. 데이터 모델 / API 개략 (spring-expert 참고)

```
Review
  id, orderItemId(FK, unique), productId(FK, 비정규화 — 조회 최적화), userId(FK)
  rating(Int 1~5), content(Text), status(VISIBLE/HIDDEN)
  createdAt/updatedAt (BaseTimeEntity)

ReviewImage
  id, reviewId(FK), imageUrl, displayOrder

ReviewReport
  id, reviewId(FK), reporterId(FK), reason, createdAt
  unique(reviewId, reporterId)  -- 중복 신고 방지

ReviewRewardPolicy (기존 PointPolicy 확장 or 신규 정책 테이블)
  textReviewPoint, photoReviewPoint, reviewableDays
```

- `Product`에 `avgRating`, `reviewCount` 컬럼을 비정규화해 둘지, 매 조회 시 집계할지는
  spring-expert 판단(트래픽에 따라). 인기상품 집계(`ProductService.getPopular`)처럼 네이티브
  집계 SQL 패턴 재사용 가능.
- 신규 마이그레이션: `reviews`, `review_images`, `review_reports` (V14~ 예상, 기존 V13 settlement
  다음 번호).

### API 개략
| 메서드 | 경로 | 설명 | 인증 |
|---|---|---|---|
| POST | `/api/reviews` | 리뷰 작성(`orderItemId`, rating, content, imageUrls) | 회원 |
| PATCH | `/api/reviews/{id}` | 본인 리뷰 수정 | 회원 |
| DELETE | `/api/reviews/{id}` | 본인 리뷰 삭제 | 회원 |
| GET | `/api/products/{productId}/reviews?sort=&photoOnly=&page=` | 상품 리뷰 목록 | 불필요 |
| GET | `/api/me/reviews` | 내가 쓴 리뷰 목록 | 회원 |
| GET | `/api/me/orders/reviewable` | 리뷰 작성 가능한 주문항목 목록 | 회원 |
| POST | `/api/reviews/{id}/reports` | 리뷰 신고 | 회원 |
| GET | `/api/admin/reviews?status=&productId=&reported=` | 관리자 리뷰 검색 | 관리자 |
| PATCH | `/api/admin/reviews/{id}/status` | 관리자 숨김/복구 | 관리자 |

## 6. 프론트 화면/플로우 개략 (react-expert · uiux-expert 참고)

- **상품 상세페이지**: 기존 `ProductDetailPage` 상단 요약 영역에 평균 평점 배지 + "리뷰 N개" 앵커
  링크 추가. 하단에 리뷰 탭 섹션 신설(정렬 드롭다운, 포토 필터 토글, 무한스크롤 또는 페이지네이션).
- **마이페이지**: "리뷰 작성 대기" 섹션 — 배송완료 후 리뷰 미작성 주문항목을 카드로 나열, CTA로
  리뷰 작성 모달/페이지 진입. `docs/design/storefront-ui-spec.md`의 카드/버튼 토큰 재사용.
- **리뷰 작성 폼**: 별점 선택(터치 타깃 ≥44px), 텍스트 영역(글자수 카운터), 이미지 업로드
  드롭존(최대 5장, 미리보기, 개별 삭제).
- **관리자 백오피스**: 기존 관리자 주문검색 화면 패턴과 동일하게 리뷰 검색 테이블 + 신고사유
  상세 다이얼로그 + 숨김/복구 액션.
- 접근성: 별점 위젯은 `role="radiogroup"`, 스크린리더용 텍스트 라벨 동반(uiux-expert가 D5/D11
  이슈 패턴과 일관되게 처리).

## 7. 기존 기능과의 연계/영향

- **order 도메인**: `SubOrder.status`를 리뷰 작성 가능 여부 판단에 참조(읽기 전용, 기존 상태
  전이 로직 변경 없음).
- **point 도메인**: 리뷰 작성 시 `PointService.earn`류 API를 재사용해 적립(신규 lot 생성).
  기존 "결제 확정 시 적립"과는 별개의 트리거이므로 적립 사유(reason) 구분 필드가 필요할 수 있음
  — `point` 도메인과 조율 필요.
- **catalog 도메인**: 상품 상세/목록 응답 DTO에 평점 요약 필드 추가(기존 `ProductResponse` 확장).
- **admin 감사로그**: 리뷰 숨김/복구는 민감 액션이므로 기존 `AuditLogFilter`에 자연히 기록됨(추가
  작업 불필요).

## 8. 범위 (In / Out of scope)

**In scope**
- 텍스트/포토 리뷰 작성·수정·삭제, 평점 집계 노출, 신고, 관리자 숨김 처리, 리뷰 적립 포인트

**Out of scope (이번 단계 제외)**
- 셀러의 리뷰 답글 기능
- AI 기반 리뷰 요약/감성분석
- 리뷰에 대한 "도움이 됐어요" 투표
- 이미지 업로드 스토리지 인프라 자체 구축(전제 조건으로만 명시)

## 9. 오픈 이슈 (결정 필요)

1. **"배송완료" 판정 방식**: 현재 SubOrder 상태가 `DELIVERED`로 전이되는 주체가 판매자 수동
   업데이트인지, 자동(예: 송장 배송완료 API 연동)인지 확인 필요. 수동이라면 실제로는
   `SHIPPED`에서 오래 머무를 수 있어 "구매확정" 자동 전이 정책(예: 배송 후 N일 자동 확정)이
   추후 필요할 수 있다.
2. **리뷰 삭제 시 포인트 회수 여부**: 어뷰징 방지 관점에서 삭제해도 회수하지 않을지, 즉시 회수할지
   운영 정책 결정 필요.
3. **평점 비정규화 여부**: 트래픽 예상 규모에 따라 `Product.avgRating` 컬럼화 vs 매 조회 집계
   결정은 spring-expert에 위임하되, 사전에 예상 리뷰/조회 비율 공유 필요.
4. **신고 임계치 자동 숨김 여부**: MVP는 "노출 유지 + 검토 큐"로 제안했으나, 운영 리소스가 부족하면
   자동 숨김 정책으로 바꿀 수 있음 — 결정 필요.
