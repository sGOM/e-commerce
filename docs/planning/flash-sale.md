# 타임딜 / 한정특가

> 우선순위: **P1** (Should)
> 관련 도메인: `catalog`(Inventory/Product), `order`(주문 시 가격 스냅샷), `settlement`(수수료 이슈)

## 1. 개요 및 배경

마켓컬리는 "오늘의 특가", 타임딜 형태로 한정 시간·한정 수량 할인을 운영해 긴급성을 만든다.
우리 플랫폼에는 쿠폰(정률/정액, 유효기간)은 있지만, "정해진 시간에만 특가가 적용되고 수량이
소진되면 즉시 종료"되는 상품 자체의 시간 한정 가격 개념은 없다. 재고 원자적 UPDATE 패턴을 거의
그대로 재사용할 수 있어 구현 난이도는 중간이지만, 할인분을 누가 부담하는지(셀러/플랫폼)는 정산과
직결되어 정책 결정이 선행되어야 한다.

## 2. 목표 및 성공지표

- 목표: 특정 옵션에 대해 한정 시간·한정 수량 특가를 운영해 단기 전환을 끌어올린다.
- 성공지표(제안)
  - 타임딜 노출 대비 클릭률, 클릭 대비 구매전환율
  - 타임딜 한도 소진율(완판율)
  - 타임딜 매출이 일반 판매를 잠식(cannibalization)하는지 여부 — 딜 종료 직후 판매량 비교

## 3. 유저 스토리 & 수용기준(AC)

### US-1. 관리자(또는 셀러, 오픈 이슈)는 타임딜을 등록한다
- AC1: 대상 옵션, 특가(salePrice, 정가보다 낮아야 함), 시작/종료 시각, 한도 수량(limitQuantity)을
  등록한다.
- AC2: 동일 옵션에 시간이 겹치는 타임딜은 등록할 수 없다(검증).

### US-2. 고객은 진행 중인 타임딜을 보고 특가로 구매한다
- AC3: 진행 중(`now ∈ [startAt, endAt)` and `soldQuantity < limitQuantity`)인 딜만 목록/상세에
  특가로 노출되고 카운트다운이 표시된다.
- AC4: 장바구니/주문 담기 시 `salePrice`가 적용되고, `OrderItem`에는 **주문 시점 스냅샷**(정가 +
  적용된 특가 + 딜 식별자)이 기록된다(기존 "주문 항목은 생성 시점 스냅샷" 원칙 그대로 적용).
- AC5: 딜 종료 시각이 지나거나 한도 수량이 소진되면 이후 요청은 정가로 처리되거나 품절 처리된다
  (한도 소진은 "품절"과는 다른 상태 — "딜 종료"로 별도 표기).

### US-3. 동시 다발 주문에도 한도 수량을 초과 판매하지 않는다
- AC6: 재고와 별개로 `soldQuantity`를 원자적 UPDATE(`WHERE soldQuantity + qty <= limitQuantity`)로
  증가시켜, 동시 요청에서도 한도를 넘기지 않는다. 재고 자체의 원자적 UPDATE와 **함께(둘 다 통과해야
  성공)** 검증해야 한다 — 재고는 충분하지만 딜 한도는 소진, 또는 그 반대 케이스 모두 있음.

### US-4. 주문이 취소되면 딜 한도가 복원된다
- AC7: 부분취소/전체취소 시 재고 `release()`와 함께 `soldQuantity`도 되돌린다(딜이 이미 종료됐어도
  복원은 수행 — 통계 정확성 목적이며 재판매 여부와는 무관).

## 4. 정책/규칙 & 예외

- **가격 결정 권한**: 최소주문금액 같은 조건 없이 옵션 단위 고정 특가. 쿠폰과의 중첩 여부는 기존
  "쿠폰은 주문에 1개만 적용" 원칙과 별개로, 타임딜가 위에 쿠폰을 추가 적용할지 여부는 정책 결정
  필요(기본 제안: 타임딜가에도 쿠폰/포인트는 정상 적용 — 쿠폰은 상품가가 아닌 주문 총액 기준
  할인이므로 자연스럽게 동작).
- **정산 영향**: `SubOrder.subtotal`은 실제 결제된 특가 기준으로 집계되므로 정산 로직 변경은
  불필요하나, **할인분을 셀러가 부담하는지 플랫폼이 보전하는지**는 별도 정산 규칙이 필요할 수
  있다(오픈 이슈 — 우선은 "셀러 부담"으로 가정, 셀러가 직접 특가를 신청하는 구조와 자연히 맞음).
- **한도 소진 표시**: "품절"과 구분되는 "타임딜 종료" 배지를 사용해 고객에게 혼선을 주지 않는다
  (재고는 남아있고 정가로는 구매 가능할 수 있음).
- **딜 시작 전 예고**: `startAt` 전에는 "오픈 예정" 배지로 노출할지 여부는 오픈 이슈.

## 5. 데이터 모델 / API 개략 (spring-expert 참고)

```
FlashSale
  id, productOptionId(FK), sellerId(FK, 비정규화 — 정산/권한 조회 편의)
  originalPrice, salePrice, limitQuantity, soldQuantity
  startAt, endAt, status(SCHEDULED/ACTIVE/ENDED/CANCELED)

OrderItem 확장
  flashSaleId(nullable FK), appliedSalePrice(nullable) -- 기존 스냅샷 필드에 추가
```

- 한도 원자적 UPDATE 쿼리 예시(기존 `InventoryRepository.reserve`와 동일 패턴):
  ```sql
  UPDATE flash_sales SET sold_quantity = sold_quantity + :qty
   WHERE id = :id AND sold_quantity + :qty <= limit_quantity
  ```
- 주문 생성 흐름에서 재고 `reserve()`와 딜 한도 증가를 **둘 다 트랜잭션 내에서 순차 검증**하고,
  어느 한쪽이라도 실패하면 전체 롤백(기존 `OrderService.buildOrder` 예외 처리 패턴 재사용).
- 신규 마이그레이션: `flash_sales`, `order_items`에 컬럼 추가.

### API 개략
| 메서드 | 경로 | 설명 | 인증 |
|---|---|---|---|
| GET | `/api/flash-sales?status=active` | 진행 중 타임딜 목록 | 불필요 |
| GET | `/api/flash-sales/{id}` | 타임딜 상세 | 불필요 |
| POST | `/api/seller/flash-sales` | 셀러 타임딜 신청(오픈 이슈에 따라 관리자 승인 필요할 수 있음) | 셀러 |
| GET | `/api/seller/flash-sales` | 본인 타임딜 목록 | 셀러 |
| POST | `/api/admin/flash-sales` | 관리자 직접 등록/승인 | 관리자 |
| PATCH | `/api/admin/flash-sales/{id}/cancel` | 강제 종료 | 관리자 |

## 6. 프론트 화면/플로우 개략 (react-expert · uiux-expert 참고)

- **홈/목록**: "타임딜" 섹션(컬렉션과 유사한 캐러셀이지만 카운트다운 타이머 + 진행률 바(소진율)
  포함). 컬렉션 컴포넌트와 카드 레이아웃을 공유하되 가격 영역에 정가 취소선 + 특가 강조.
- **상품 상세**: 진행 중 딜이 있으면 상단에 카운트다운 배너, 가격 표시를 정가 대신 특가로 전환.
  종료 임박(예: 10분 이내)은 경고색 강조.
- **판매자 백오피스**: 타임딜 신청 폼(옵션 선택, 특가, 기간, 수량) + 신청 상태 목록.
- **관리자 백오피스**: 승인 대기 목록(오픈 이슈에 따라), 강제 종료 액션.
- 카운트다운은 서버 시각 기준으로 재계산(클라이언트 시계 신뢰 금지 — 서버가 `endAt`을 내려주고
  클라이언트는 로컬에서 표시만).

## 7. 기존 기능과의 연계/영향

- **catalog 도메인**: `ProductOption` 조회 시 진행 중 딜이 있으면 응답에 딜 정보 포함(가격 오버라이드).
- **order 도메인**: `OrderService.buildOrder`에 딜 한도 검증 단계 추가. 취소 캐스케이드
  (`cancelSubOrder`)에 딜 한도 복원 단계 추가.
- **settlement 도메인**: 별도 로직 변경은 없으나, 할인분 부담 주체 정책에 따라 셀러 정산 금액
  계산식이 달라질 수 있어 정책 확정 후 재검토 필요.

## 8. 범위 (In / Out of scope)

**In scope**
- 옵션 단위 타임딜 등록/노출/한도 동시성 제어, 주문 스냅샷, 취소 시 한도 복원

**Out of scope**
- 복수 옵션 묶음 딜(세트 특가)
- 개인화 타임딜(고객 세그먼트별 다른 특가)
- 딜 예약 알림("시작하면 알려줘") — 재입고 알림과 유사한 별도 기능으로 후속 검토

## 9. 오픈 이슈 (결정 필요)

1. **셀러 직접 신청 vs 관리자 전용**: 셀러가 자율적으로 타임딜을 걸게 할지, 관리자 승인을 거치게
   할지. 후자가 안전하지만 운영 리소스가 필요.
2. **할인분 부담 주체**: 셀러 100% 부담인지, 플랫폼이 일부 보전하는 프로모션 예산 개념을 둘지.
   정산 계산식에 직접 영향을 주므로 spring-expert 착수 전 확정 필요.
3. **쿠폰과의 중첩 허용 여부**: 타임딜가 위에 쿠폰까지 중첩 적용을 허용할지, 타임딜 참여 상품은
   쿠폰 적용 대상에서 제외할지.
