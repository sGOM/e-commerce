# 재입고 알림

> 우선순위: **P0** (Must)
> 관련 도메인: `catalog`(Inventory/Product), `seller`(재고 조정), `notification`(신규, 최소 인앱)

## 1. 개요 및 배경

마켓컬리는 품절 상품에 "재입고 알림 신청" 버튼을 제공해, 이탈했을 고객의 수요를 붙잡아 둔다.
우리 플랫폼은 이미 품절 상품을 "노출하되 구매 차단"하는 정책(`PRD.md` 5.1)이 있어 품절 UX 기반은
갖춰져 있지만, 그 이후 고객이 다시 방문하게 만드는 장치가 없다. 재고는 이미 원자적 UPDATE로
정합성이 보장되어 있으므로(`InventoryRepository.reserve/release`), 재입고 감지 훅을 얹는 비용이
낮아 P0로 분류했다.

## 2. 목표 및 성공지표

- 목표: 품절 옵션에 대해 회원이 알림을 신청하고, 재고 보충 시 1회 알림을 받아 재방문·재구매로
  이어지게 한다.
- 성공지표(제안)
  - 품절 상품 페이지 방문 대비 알림 신청률
  - 알림 발송 후 N시간 내 재방문/구매 전환율
  - 재입고 알림이 촉발한 매출(알림 클릭 → 구매 추적)

## 3. 유저 스토리 & 수용기준(AC)

### US-1. 회원은 품절 옵션에 재입고 알림을 신청할 수 있다
- AC1: 대상 `ProductOption`의 가용재고(`quantity - reserved`)가 0일 때만 신청 버튼이 활성화된다.
- AC2: 이미 신청 중(`PENDING`)인 옵션은 중복 신청 불가(버튼이 "신청됨"으로 바뀌고 취소 가능).
- AC3: 게스트는 신청 시 로그인 유도(회원 전용) — 별도 이메일 입력 신청은 out of scope(오픈 이슈).

### US-2. 회원은 신청을 취소할 수 있다
- AC4: 마이페이지에서 신청 목록을 보고 개별 취소 가능.

### US-3. 재고가 보충되면 신청자에게 알림이 간다
- AC5: 판매자/관리자가 재고를 0 → 1 이상으로 조정(`PATCH /api/seller/products/{id}/stock` 등)하는
  순간, 해당 옵션에 대한 `PENDING` 알림 신청 전체가 `NOTIFIED`로 전이되고 인앱 알림이 생성된다.
- AC6: 알림은 옵션당 1인 1회만 발송한다. 이후 재신청 전까지 같은 재고 변동으로 재발송하지 않는다
  (예: 재고가 1→0→1로 다시 바뀌어도 이미 NOTIFIED된 사용자는 재발송 대상이 아님).
- AC7: 알림 발송은 재고 보충 트랜잭션의 **성공 이후 비동기**로 처리해 재고 갱신 자체를 지연시키지
  않는다(감사로그의 `@Async` 패턴과 동일 원칙).

### US-4. 회원은 인앱 알림함에서 재입고 소식을 확인하고 상품으로 이동한다
- AC8: 알림함에서 미확인 개수 배지, 클릭 시 상품 상세로 이동 및 읽음 처리.

## 4. 정책/규칙 & 예외

- **신청 가능 조건**: 옵션 단위(색상/사이즈 등 SKU 단위) — 상품 단위가 아님. 같은 상품의 다른
  옵션은 재고가 있을 수 있으므로 옵션 단위 정밀도가 맞다.
- **품절 → 재입고 판정**: `quantity - reserved`가 0에서 1 이상으로 전이되는 순간을 트리거로 삼는다.
  예약(reserved) 증가로 인한 가용재고 감소는 트리거 대상이 아니다(신규 입고분 증가만 대상).
- **상품 자체가 숨김/삭제된 경우**: 재고가 늘어도 `Product.status`가 비공개면 알림 발송하지 않고,
  발송 대기 상태를 유지하거나 만료 처리(오픈 이슈).
- **알림 재발송 방지**: `NOTIFIED` 상태는 소멸성 — 사용자가 다시 관심 있으면 재신청해야 한다(스팸
  방지 및 데이터 단순화).
- **대량 발송 스로틀링**: 인기 옵션이 재입고되면 신청자가 많을 수 있으므로 배치/큐 처리를 전제로
  한다(동기 처리 금지).

## 5. 데이터 모델 / API 개략 (spring-expert 참고)

```
RestockAlert
  id, userId(FK), productOptionId(FK)
  status(PENDING/NOTIFIED/CANCELED)
  createdAt, notifiedAt
  unique(userId, productOptionId, status='PENDING')  -- 부분 유니크 or 애플리케이션 체크

Notification (신규 공통 도메인, 재입고 외 다른 알림에도 재사용 가능하도록 범용 설계 권장)
  id, userId(FK), type(RESTOCK/…), title, body, linkUrl
  isRead(Boolean), createdAt
```

- 재고 조정 API(`InventoryService` 내 재고 증가 경로)에서 "이전 가용재고 0 → 증가 후 >0"을 감지해
  `RestockAlertService.triggerNotifications(optionId)`를 호출하는 훅 구조 제안. 트랜잭션 커밋 이후
  이벤트 발행(`ApplicationEventPublisher` + `@TransactionalEventListener(AFTER_COMMIT)`)으로 재고
  갱신과 알림 발송을 분리하는 것을 권장(spring-expert 확정 필요).
- 신규 마이그레이션: `restock_alerts`, `notifications`.

### API 개략
| 메서드 | 경로 | 설명 | 인증 |
|---|---|---|---|
| POST | `/api/products/options/{optionId}/restock-alerts` | 알림 신청 | 회원 |
| DELETE | `/api/products/options/{optionId}/restock-alerts` | 알림 취소 | 회원 |
| GET | `/api/me/restock-alerts` | 내 신청 목록 | 회원 |
| GET | `/api/me/notifications?unreadOnly=` | 내 알림함 | 회원 |
| PATCH | `/api/me/notifications/{id}/read` | 읽음 처리 | 회원 |

## 6. 프론트 화면/플로우 개략 (react-expert · uiux-expert 참고)

- **상품 상세**: 품절 옵션 선택 시 "담기" 버튼 자리에 "재입고 알림 신청" 버튼으로 대체(기존
  D8 상태 배지 개선과 함께, 품절 배지를 명확한 경고색으로). 신청 후 토스트 + 버튼 상태 전환.
- **헤더**: 기존 장바구니 배지 옆에 알림 벨 아이콘 + 미확인 개수 배지 신설(Layout.tsx의 D12
  모바일 네비 과밀 이슈와 함께 정리 필요 — uiux-expert에 위임).
- **알림함 드롭다운/페이지**: 리스트형, 미확인은 강조 배경, 클릭 시 해당 상품으로 이동 + 읽음 처리.
- **마이페이지**: "재입고 알림 신청 목록" 탭 — 상품 썸네일/옵션명/신청일/취소 버튼.

## 7. 기존 기능과의 연계/영향

- **catalog 도메인**: `InventoryService`의 재고 증가 경로(판매자 재고 조정 `PATCH .../stock`,
  향후 입고 API)에 훅 추가. 기존 원자적 UPDATE 자체는 변경하지 않고 "성공 후 이벤트 발행"만 추가.
- **seller 백오피스**: 셀러가 재고를 늘리는 시점이 곧 트리거이므로, 셀러 상품 관리 화면에는 특별한
  변경이 필요 없다(부작용으로 알림이 나간다는 점만 내부 문서화).
- **admin**: 신규 `notifications` 발송량 모니터링 필요 시 관리자 대시보드 확장 여지(이번 범위 밖).

## 8. 범위 (In / Out of scope)

**In scope**
- 옵션 단위 재입고 알림 신청/취소, 재고 보충 트리거 감지, 인앱 알림함, 1인 1회 알림 원칙

**Out of scope**
- 이메일/푸시 발송(인프라 부재, 공통 오픈이슈 3 참고) — 인앱 알림함으로 대체 후 후속 확장
- 게스트(비회원) 이메일 등록 알림
- 가격 인하 알림(재입고와 별개 기능, 추후 별도 기획)

## 9. 오픈 이슈 (결정 필요)

1. **게스트 알림 지원 여부**: 이메일만 받아 발송하는 게스트용 알림을 이번에 포함할지, 회원 전용으로
   시작할지 — 회원 전용으로 시작하는 것을 제안하나 마케팅 관점에서 게스트 리드 확보 니즈가 있다면
   재검토 필요.
2. **Notification 엔티티의 범용성**: 재입고 알림 전용으로 좁게 설계할지, 향후 주문상태변경/쿠폰 등
   다른 알림도 담을 범용 테이블로 설계할지 — 범용으로 제안하되 spring-expert와 스키마 확정 필요.
3. **알림 발송 트리거 시점**: 판매자가 재고를 여러 번 나눠 조정(0→3→0→5)할 때 이벤트가 여러 번
   발생할 수 있다. 트랜잭션 이벤트 리스너의 정확한 "이전 값" 판단 방식(조회 후 UPDATE vs UPDATE
   결과 비교)은 spring-expert가 재고 원자적 UPDATE 패턴과 충돌 없이 설계해야 한다.
