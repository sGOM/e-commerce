# 선물하기

> 우선순위: **P2** (Could — 기존 주문 전제와 충돌 지점 존재)
> 관련 도메인: `order`(주소 없는 주문/수령 확정), `payment`, 신규 `gift`(가칭) 도메인

## 1. 개요 및 배경

마켓컬리는 상품을 구매해 카카오톡 등으로 선물하고, 수령자가 직접 배송지를 입력하게 하는
"선물하기" 플로우를 지원한다. 구매자는 상대방 주소를 몰라도 선물할 수 있어 신규 유입·바이럴
채널로 기능한다. 우리 플랫폼의 주문 생성은 현재 배송지가 필수 전제로 보이며(SubOrder에 배송지
연결), "결제는 됐지만 배송지는 나중에 정해지는" 상태를 표현하는 개념이 없다. 이 충돌 지점 때문에
난이도가 상대적으로 높아 P2로 분류한다.

## 2. 목표 및 성공지표

- 목표: 구매자가 배송지 없이 결제하고, 수령자가 링크를 통해 배송지를 입력하면 배송이 시작되는
  플로우를 제공한다.
- 성공지표(제안)
  - 선물 주문 비율, 선물 링크 수락률(전송 대비 수령자 배송지 입력 완료 비율)
  - 선물 수신자의 신규 가입 전환율(바이럴 유입 지표)

## 3. 유저 스토리 & 수용기준(AC)

### US-1. 구매자는 배송지 없이 선물 주문을 결제한다
- AC1: 주문 생성 시 `isGift = true`로 표시하면 배송지 입력을 생략하고 결제까지 진행할 수 있다.
- AC2: 결제는 정상적으로 즉시 처리된다(구매자 카드 청구는 수령자 입력을 기다리지 않음).
- AC3: 선물 메시지(선택, 텍스트)를 함께 등록할 수 있다.

### US-2. 구매자는 수령자에게 공유 가능한 링크를 받는다
- AC4: 주문 완료 시 `GiftClaim` 토큰이 발급되고, 공유 가능한 URL(`/gift/{token}`)이 제공된다.
- AC5: 링크는 만료기한(정책값, 예: 7일)을 가진다.

### US-3. 수령자는 로그인 없이 배송지를 입력해 수락한다
- AC6: 링크 접속 시 선물 메시지/보낸 사람 정보(선택 노출)와 함께 배송지 입력 폼이 보인다.
- AC7: 배송지 입력 완료 시 해당 SubOrder(들)에 배송지가 연결되고 배송 준비가 시작될 수 있는
  상태(`PAID` → 배송지 확정)로 전이된다.
- AC8: 이미 수락된 링크는 재사용 불가(1회성).

### US-4. 수령자가 기한 내 미수락 시 자동 취소·환불된다
- AC9: 만료기한 경과 시 배치가 미수락 선물 주문을 자동 취소하고 전액 환불한다(기존 취소/환불
  로직 재사용).
- AC10: 구매자에게 만료 임박/취소 안내 알림을 보낸다.

### US-5. 구매자는 수령자가 배송지를 입력하기 전까지 선물을 취소할 수 있다
- AC11: 배송지 입력(수락) 전이라면 구매자가 직접 취소 가능(전액 환불). 수락 이후에는 일반 주문과
  동일한 취소 정책(배송 전까지만 등)을 따른다.

## 4. 정책/규칙 & 예외

- **멀티셀러 선물 주문**: 여러 SubOrder가 있는 선물 주문이라면, 수령자는 한 번의 배송지 입력으로
  모든 SubOrder에 동일 배송지를 적용한다(선물은 단일 수령자가 자연스러움 — SubOrder별로 다른
  주소를 받는 케이스는 범위 밖).
- **쿠폰/포인트**: 구매자의 쿠폰/포인트만 사용 가능(수령자 것 아님). 기존 정책과 동일.
- **게스트 선물**: 구매자는 회원 전용(주문 관리/알림 필요), 수령자는 비회원도 가능(링크 기반,
  회원가입 불필요 — 바이럴 유입 목적에 부합).
- **개인정보**: 수령자가 입력한 배송지는 구매자에게 노출하지 않는다(선물 특성상 프라이버시 보호,
  기존 주문 상세 응답에서 배송지 필드 마스킹 필요).

## 5. 데이터 모델 / API 개략 (spring-expert 참고)

```
Order 확장
  isGift(Boolean), giftMessage(nullable Text)
  -- 기존 배송지 FK는 선물 주문일 때 초기 null 허용 필요 (기존 필수 제약 완화)

GiftClaim
  id, orderId(FK), token(Unique, 랜덤), status(PENDING/CLAIMED/EXPIRED/CANCELED)
  expiresAt, claimedAt, recipientAddressId(FK, nullable until claimed)
```

- **기존 아키텍처와의 충돌**: 현재 `Order`/`SubOrder`가 생성 시점에 배송지를 요구한다면(정확한
  현재 구현은 spring-expert 확인 필요), 선물 주문을 위해 **배송지 nullable 허용 + "배송지 확정
  전에는 SHIPPED로 전이 불가"라는 상태 가드**를 추가해야 한다. 이는 기존 주문 상태 전이 로직에
  대한 침습적 변경이므로 신중한 설계가 필요.
- 신규 마이그레이션: `orders` 컬럼 추가, `gift_claims` 신설.

### API 개략
| 메서드 | 경로 | 설명 | 인증 |
|---|---|---|---|
| POST | `/api/orders` (body에 `isGift`, `giftMessage`) | 선물 주문 생성(배송지 생략) | 회원 |
| GET | `/api/gift/{token}` | 선물 정보 미리보기(메시지/보낸사람/상품 요약) | 불필요 |
| POST | `/api/gift/{token}/claim` | 배송지 입력 및 수락 | 불필요 |
| POST | `/api/orders/{id}/gift/cancel` | 구매자가 수락 전 취소 | 회원 |
| GET | `/api/admin/gift-claims?status=` | 관리자 모니터링(만료 임박 등) | 관리자 |

## 6. 프론트 화면/플로우 개략 (react-expert · uiux-expert 참고)

- **체크아웃**: "선물하기" 토글 → 켜면 배송지 스텝이 "선물 메시지 작성" 스텝으로 대체.
- **주문 완료 화면**: 공유 링크 + 카카오톡 공유 버튼(웹 공유 API 또는 링크 복사로 단순화 가능).
- **선물 수락 페이지(`/gift/:token`)**: 비로그인 접근 가능한 별도 레이아웃(헤더 축소), 메시지
  카드 + 상품 미리보기 + 배송지 입력 폼.
- **마이페이지**: 보낸 선물 목록(수락 대기/완료/만료 상태 배지).

## 7. 기존 기능과의 연계/영향

- **order 도메인**: 배송지 필수 제약 완화가 가장 큰 영향. 상태 전이 가드(배송지 없이는 SHIPPED
  불가) 추가 필요 — 기존 `SubOrder` 상태 머신에 조건부 분기가 생긴다.
- **payment 도메인**: 결제 자체는 기존 플로우 그대로(구매자가 결제, 수령자는 결제 무관).
- **알림**: 만료 임박 안내 등은 `restock-alert.md`에서 제안한 `Notification` 공용 테이블 재사용
  가능.

## 8. 범위 (In / Out of scope)

**In scope**
- 배송지 없는 선물 결제, 공유 링크, 수령자 배송지 입력, 미수락 자동 취소/환불

**Out of scope**
- 선물 포장/카드 옵션(실물 포장 SKU 관리)
- SubOrder별 개별 수령자(한 주문 내 여러 명에게 나눠 보내기)
- 수령자가 다른 상품으로 교환하는 "리퀘스트" 기능

## 9. 오픈 이슈 (결정 필요)

1. **현재 주문 생성 로직의 배송지 필수 여부 확인**: `PRD.md`상 명시적으로 "필수"라고 단정하기
   어려워, spring-expert가 실제 코드(`OrderService.createFromCart` 등)를 확인해 배송지 nullable
   허용의 영향 범위를 먼저 진단해야 한다.
2. **미수락 만료 기한/환불 정책**: 7일을 기본값으로 제안했으나 운영 정책 확정 필요.
3. **수령자 개인정보 노출 범위**: 구매자에게 "수락 완료 여부"만 보여줄지, 배송 상태까지 보여줄지.
4. **우선순위 재검토 시점**: README 인덱스에 명시했듯 이번 분기는 Won't(보류)로 제안 — 다른 P0/P1
   기능 이후 트래픽 데이터를 보고 재평가.
